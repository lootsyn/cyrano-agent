## 실행 순서

1. 입력 artifact와 선행 evidence의 digest·실행 상태를 확인한다. 문서만 있는 선행 작업을 통과로 취급하지 않는다.
2. 구현 계획에 public API, 변경 경로, 불변 조건, positive/negative test, 외부 side effect, rollback을 적는다. 독립 reviewer의 mandatory finding을 먼저 해결한다.
3. 아래 acceptance ID마다 재현 가능한 거부/정상 테스트를 먼저 작성한다. 현재 기반 unit 사례를 복사해 product 통합 사례가 된 것처럼 이름만 바꾸지 않는다.
4. 명세의 결정적 부분부터 구현하고 실제 provider/host 연결은 명시 port로 결합한다. 미지원 기능은 typed unsupported로 반환한다.
5. timeout·cancel·late result·partial startup·duplicate request·scope mismatch를 포함해 구현한다. 실패를 success/empty default로 감추지 않는다.
6. 작성한 targeted test와 schema/문서/기반 회귀/품질 검사를 실행한다. 실제 runtime 또는 paid model이 필요한 부분은 별도 허가가 없으면 not_run으로 보고한다.
7. 담당 설계·schema·config·fixture·문서 라우터를 같은 변경에서 갱신한다. generated full design을 재생성한다.
8. independent result review 뒤 evidence를 작성하고 모든 mandatory gate 통과 시만 WP를 verified로 바꾼다.

## 실패·복구

코드 변경은 허가된 개발 작업 사본 안에 보존한다. 기존 failing baseline과 신규 failure를 분리해 기록한다. 데이터 migration·원본 변경·외부 호출은 해당 approval과 복구 recipe 없이 되돌리지 않는다. unknown external outcome은 reconciliation한다. 선행 API 변경으로 실패하면 임의 fallback 대신 소유 WP와 contract를 함께 수정한다.

## 평가·native 배치 실행 계약

기존 독립 workspace 경로 대신 `libs/code/deepagents_code/cyrano/`와 native test 트리를 사용한다. pyproject/lock/native entrypoint는 이 WP의 허가 없이 덮어쓰지 않는다. 작업은 [테스트 개발 실행계획](../../docs/development/TEST_DEVELOPMENT_PLAN.ko.md)을 우선하고 모든 승인을 현재 plan digest에 결속한다.

### TS01: 평가 계약·신뢰된 증거·점수 판정

구조검사와 서명/원장 검증을 분리한다. 공개 도구에서 점수·서명·숨은 oracle에 쓰기 접근을 주지 않는다. fixture PASS·빈 suite·다른 snapshot·만료 reviewer·중복 결과·실패 재시도 숨기기를 모두 차단한다.

계약 함수: `create_assessment_session -> AssessmentSession`; `register_case_attempt -> Receipt`; `verify_evidence_bindings -> VerifiedEvidence`; `decide_atom -> AtomDecision`; `finalize_scorecard -> AssessmentReport`

### TS08: 개선 전후·회귀·다음 작업 적용

경로 B는 입력 변경이므로 새 actual run을 사용한다. baseline/candidate를 같은 snapshot/runtime/budget으로 비교하고 family split·고정 분석방법·confidence와 비용을 기록한다. inconclusive는 유지하며 parent CAS 승격 후 새 task만 새release를 받는지 확인한다.

계약 함수: `seal_experiment -> EvaluationManifest`; `run_paired_trials -> TrialLedger`; `decide_effect -> EffectVerdict`; `promote_release -> Release`; `rollback_release -> Receipt`

### TS11: 실제 통합·CI·점수·출시 evidence

upstream 회귀와 CYRANO owned delta를 모두 검사한다. zero/skip/xfail/deselected를 mandatory PASS로 처리하지 않고 source가 바뀌면 증거를 다시 생성한다. native install/wheel/entrypoint와 실제 branch protection을 검증한 뒤 운영자가 결과를 확정한다.

계약 함수: `collect_exact_nodeids -> CollectionReceipt`; `run_release_matrix -> ExecutionReceipts`; `verify_required_checks -> RemotePolicyEvidence`; `publish_assessment -> AssessmentReport`

수용 case ID는 plan.json acceptance_ids 및 tests/assessment/cases.json을 따른다. 문서·fixture 검사는 preparation이며 제품 점수는 trusted 실제 실행과 독립 review 이후에만 요청한다.

### paired 평가·fault model·effectiveness 증거

인터페이스: `EvaluationPlan, EvidenceBundle; paired task-family analysis and hard gate.`. 자세한 타입·오류·트랜잭션은 [담당 설계](../../docs/design/RELEASE_ASSETS_AND_OPERATIONAL_COMPLETENESS.ko.md)를 따른다.

1. 현baseline과candidate를immutablemanifest로고정한다. source/runtime/policy/suite/model/route/budget 차이를명시한다.
2. 동일task/differentharness와동일harness/differentmodel비교를분리한다. task family와시간으로split하고holdout 노출제한을둔다.
3. 정확성·firstpass·false-ready·scope위반·testpass·humanintervention·retry·token/cache/cost/latency를 실제관측으로정의한다.
4. counterbalance 실행순서,cachewarm/cold 관측가능성,환경오류·실패·중단표본을그대로보존한다. 무작위seed를API가 지원하지 않으면unknown이라고적는다.
5. 성능개선CI와non-inferiority margin은실험전에등록한다. 공백·insufficientpower는inconclusive. 이작업의평가계약은WP16전에정의하고effectiveness 실행은제품연결후수행한다.

수용 조건: safety regression 상쇄0; 원본family 누수0; 모델2개를동일cache로간주하지않음; 성공모델순위대신조건별결과; fixture pass≠제품효과.

변경 파일: `../deepagents_code/cyrano/evaluation/gates.py`, `../deepagents_code/cyrano/evaluation/assessment.py`, `tests/assessment/`.

실제 제품 테스트는 다음 파일을 구현한 후 실행한다. 미구현/0건 수집/필수 skip은 통과가 아니다.

```bash
uv run --no-sync python -m pytest tests/cyrano_product/test_wp20_paired_evaluation.py -q
```

실행 전제: Required predecessor ports + real dcode adapter + explicit runtime cost/side-effect permit; missing prerequisites are blocked, not pass.

위험·금지: 개선 비용·실험 비용을 제외하면 순효과가 과대평가된다.

## 선행 조건 판정

선행 WP는 plan.json의 `dependency_milestones`에 따라 실제 구현된 `interface_ready` 포트 evidence를 제공해야 한다. 선언이나 mock만으로 충족하지 않는다. 자신의 전체 native 수용은 `product_verified`에서 별도로 수행한다. 모든 제품 요구를 실행하지 않은 상태는 최종 출시/점수 통과가 아니다.
