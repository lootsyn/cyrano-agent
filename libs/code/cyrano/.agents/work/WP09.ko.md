상태: planned. 기존 foundation이 일부 원리를 구현했더라도 이 작업의 product-level 완료를 의미하지 않는다.

## 함수·메서드 계약

- `compile_plan -> bundle`
- `validate_plan -> violations`
- `reserve_ready_work -> lease`
- `review_plan -> findings`

각 메서드는 입력 parsing/권한/revision/snapshot 확인과 실제 처리의 소유자를 분리한다. wire field 이름은 schema를 따른다. read-only는 Scope ACL 확인 뒤 수행하고 mutation은 command→transaction→event/outbox를 사용한다. 오류 enum과 next_allowed_action을 명시한다.

## 실행 순서

1. 입력 artifact와 선행 evidence의 digest·실행 상태를 확인한다. 문서만 있는 선행 작업을 통과로 취급하지 않는다.
2. 구현 계획에 public API, 변경 경로, 불변 조건, positive/negative test, 외부 side effect, rollback을 적는다. 독립 reviewer의 mandatory finding을 먼저 해결한다.
3. 아래 acceptance ID마다 재현 가능한 거부/정상 테스트를 먼저 작성한다. 현재 기반 unit 사례를 복사해 product 통합 사례가 된 것처럼 이름만 바꾸지 않는다.
4. 명세의 결정적 부분부터 구현하고 실제 provider/host 연결은 명시 port로 결합한다. 미지원 기능은 typed unsupported로 반환한다.
5. timeout·cancel·late result·partial startup·duplicate request·scope mismatch를 포함해 구현한다. 실패를 success/empty default로 감추지 않는다.
6. 작성한 targeted test와 schema/문서/기반 회귀/품질 검사를 실행한다. 실제 runtime 또는 paid model이 필요한 부분은 별도 허가가 없으면 not_run으로 보고한다.
7. 담당 설계·schema·config·fixture·문서 라우터를 같은 변경에서 갱신한다. generated full design을 재생성한다.
8. independent result review 뒤 evidence를 작성하고 모든 mandatory gate 통과 시만 WP를 verified로 바꾼다.

실행 디렉터리: monorepo의 `libs/code`. 실제 dcode 의존성 설치 후 `uv run`으로 native 통합 검사한다. 아래 기반 도구는 별도 제품 통과를 주장하지 않는다.

## 실패·복구

코드 변경은 허가된 개발 작업 사본 안에 보존한다. 기존 failing baseline과 신규 failure를 분리해 기록한다. 데이터 migration·원본 변경·외부 호출은 해당 approval과 복구 recipe 없이 되돌리지 않는다. unknown external outcome은 reconciliation한다. 선행 API 변경으로 실패하면 임의 fallback 대신 소유 WP와 contract를 함께 수정한다.

### TS05: 승인 전 수정 차단·재검토 강제

각 실제 mode와 edit/shell/MCP/child/ACP/YOLO/resume 경로에서 무승인 mutation을 시도한다. 이벤트상의 deny뿐 아니라 inode/bytes pre-post와 외부 side effect 부재를 독립 runner가 확인한다. symlink/hardlink와 old permit CAS를 포함한다.

계약 함수: `approve_plan -> ApprovalReceipt`; `authorize_execution -> ExecutionPermit`; `validate_action_scope -> Decision`; `apply_patch_via_broker -> Snapshot`; `invalidate_on_scope_change -> Revocation`

### 계획을 제한된 WorkflowIR로 검토·컴파일

인터페이스: `WorkflowCompiler.compile/propose_expansion; existing HumanDecision/Review workflow.`. 자세한 타입·오류·트랜잭션은 [담당 설계](../../docs/design/features/2026-09-16-plan-memory-execution.ko.md)를 따른다.

1. 필수 interview 결과와 기존 현재 review/approval subject를 immutable input으로 받는다. 새 schema가 자동 실행 허가를 만들지 않게 한다.
2. 허용 node kind와 typed condition AST를 parse하고 task별 요구·테스트·scope·output contract를 검증한다.
3. topological order·resource conflict·budget upper bound·hidden acceptance obligation을 계산한다. 모든 blocker의 구체 ID와 해결 owner를 돌려준다.
4. 동적 확장은 parent digest와 새 revision을 만들며 범위·비용·검증 확대를 검출해 재검토한다.
5. 조건부 사용자 응답·stale UI·취소·review loop cap을 기존 상태기계의 의미와 연결한다. 단계 축약으로 interview를 없애지 않는다.

수용 조건: cycle·임의 code expression 거부; 필수 review가 없는 plan은 dispatch0; 조건부 승인 후 수정본 재표시; 새 task가 parent permit으로 권한 확대 불가.

1. 단일 transaction에서 ready/permit/dependency 확인, lease 발급, fencing 증가와 outbox를 commit한다.

### 계획·리뷰·사람 결정의 구현 순서

1. `planning/subject.py`에서 PlanReviewSubject와 영향범위를 계산한다. 진행률·nonce·receipt를 subject에 넣지 않는다.
2. `planning/validation.py`에서 required coverage, DAG, effect scope, test binding을 검사한다. 필수 의무가 없으면 review 요청 전에 block한다.
3. `planning/review.py`에서 reviewer assignment를 source/subject에 결속하고 finding 해결을 원 reviewer 또는 독립 adjudicator가 판정하도록 한다.
4. `planning/decisions.py`에서 DecisionRequest를 저장하고 display digest·nonce·actor·scope를 검증한다. 조건부 yes는 수정 요청이지 승인이 아니다.
5. `workflow/dispatch.py`는 별도의 ExecutionPermit를 소비한다. 단순 계획 승인은 쓰기를 허가하지 않는다.
6. `planning/changes.py`에서 영향을 받는 의무·작업·review·승인의 역방향 closure를 무효화한다. telemetry sequence와 control revision을 분리한다.
7. `planning/recovery.py`에서 기존 pending decision을 다시 표시한다. LangGraph interrupt 전의 코드가 재실행되어도 요청·예약·도구 효과를 중복 생성하지 않는다.
8. `planning/completion.py`에서 최종 산출물의 숨은 평가·독립 리뷰·인수·apply/publication을 각각 판정한다.

파일 경로는 `../deepagents_code/cyrano/` 아래다. 타입은 `contracts/v2/planning.schema.json`과 기존 governance 정의를 사용하고, F0는 `tests/assessment/planning-fixtures.json`이다. 실제 통합 시험에서는 mocked authority를 제품 허가로 사용하지 않는다.

### 사례별 실행 명세 조회

`python cyrano/scripts/case_route.py --task WP09`는 사례 ID와 입력·판정을 출력한다. `--case <ID>`로 한 사례의 단계·원시 증거·복구를 읽는다. 이는 명세 조회이며 테스트 실행이 아니다.

## 선행 조건 판정

선행 WP는 plan.json의 `dependency_milestones`에 따라 실제 구현된 `interface_ready` 포트 evidence를 제공해야 한다. 선언이나 mock만으로 충족하지 않는다. 자신의 전체 native 수용은 `product_verified`에서 별도로 수행한다. 모든 제품 요구를 실행하지 않은 상태는 최종 출시/점수 통과가 아니다.
